# Benchmark Artifacts

This directory is the checked-in publication root for reproducible HIRN-Bench output.

Use it for publishable manual or nightly runs, not for ad hoc local smoke tests. PR smoke and developer sanity checks should continue to use the fast pseudo-embedding path unless you are intentionally publishing evidence.

## What Is Here

Only artifacts a **current claim depends on**. Every one is a paired `.md` (human-readable)
and `.json` (machine-readable) emission from a single run, so `run_id`, generated-at time,
and results are identical across the two.

| Artifact | What it measures |
|---|---|
| `longmemeval-oracle-temporal-ledger-dated` | Current headline run — full 500-question oracle protocol |
| `longmemeval-oracle-temporal-ledger-control` | Its paired control (`--no-temporal-ledger`) |
| `nlu-routing` | Query-view routing — the surface LongMemEval never reaches |
| `advanced-history.json` | Not an artifact: the rolling tracker the advanced suite appends to via `--tracker` |

### Retention

**A result is kept only while something claims it.** When a run is superseded, its artifact
goes and its conclusion stays in prose — that is the part which carried forward. A directory
of every run ever made is an archive, and an archive of near-identical numbers is mostly a
supply of wrong figures for someone to quote later.

Two things are never dropped:

- **The control arm of a current result.** "+17 questions at *p* = 0.0015" is not a claim
  about one run; it is a claim about a difference. Publishing the treatment alone would leave
  a number nobody can check.
- **A result measuring a different surface.** `nlu-routing` is not an older LongMemEval run,
  so nothing supersedes it.

Superseded artifacts are recoverable from git once committed. Re-running is also a documented
command, not a lost capability — every protocol in this file states how to regenerate it.

## Required Metadata For Publishable Runs

- generated-at timestamp / run date
- git SHA or release tag
- Cargo.lock blake3 (or equivalent dependency lock fingerprint)
- dataset/source name
- embedding model label
- environment label
- active retrieval surfaces, including corpus isolation protocol
- versioned reader prompt strategy when an LLM reader runs
- reproducibility drift summary when `--runs > 1`

## Review Rule

Target tables in the docs are goals. Competitor-comparison or benchmark-leadership claims should only be made when the corresponding artifact generated by the documented commands is checked in here and reviewable in git.

When publishing paired Markdown/JSON/CSV artifacts for the same run, prefer one benchmark execution plus companion output flags such as `--json-output` or `--markdown-output`. That keeps `run_id`, generated-at time, and measured results identical across the emitted files.

## Query-Intent Routing Evidence

`nlu-routing.md` / `nlu-routing.json` measure query-view routing directly — the surface
LongMemEval and HIRN-Bench do not reach, since both exercise `recall_view()` and
compiled HirnQL rather than `smart_recall`.

46 labeled queries against `gpt-4o-mini` → `text-embedding-3-small`: the model-backed
chain scores 0.9783 (95% CI 0.935–1.000) versus 0.4348 (0.283–0.587) for the deterministic
cue fallback, against a 0.2609 majority-class baseline, at roughly 1 s added median latency
per routed query. The intervals do not overlap.

The queries share no overlap with `QUERY_INTENT_TASK`'s few-shot exemplars — a build guard
enforces this, after an earlier 36-query version was found to be 19.4% contaminated and its
result withdrawn. Read the fallback's 0.4348 against the 0.2609 baseline: outside its design
envelope, cue matching barely beats a constant answer.

Regenerate with:

```bash
cargo run -p hirn-bench -- nlu-routing \
  --environment-label <label> \
  --json-output bench-results/nlu-routing.json \
  --markdown-output bench-results/nlu-routing.md
```

## LongMemEval Regression Check (M-06 migration)

`longmemeval-oracle-nlu-migration.md` / `.json` re-run the full 500-question oracle
protocol on the tree after the language-understanding migration, against the same pinned
dataset hash and the same `gpt-4o` reader/judge at temperature 0.

Retrieval is unchanged to four decimal places (containment 0.7869, recall accuracy
0.4560, abstention 27/30) and four of six reader categories are bit-identical. Official
reader accuracy reads 0.6740 versus the 0.6800 baseline — three queries out of 500, with
retrieval identical, which is reader non-determinism rather than a code effect. A single
run per arm is not a confidence interval; this rules out a material regression, nothing
more.

> `$LONGMEMEVAL_ORACLE_DIR` must contain **only** the oracle split. The dataset hash
> covers every file in the directory, so a cache holding `longmemeval_s`/`_m` as well
> hashes three files and the run is correctly refused.

The artifact itself is not retained — the conclusion above is what carried forward, and
re-running the protocol is a documented command rather than a lost file.

## Current LongMemEval Evidence

The current run and its paired control are checked in. Both use each question's official
haystack before retrieval. Superseded runs are not retained — see [Retention](#retention).

| Artifact | Reader accuracy | Containment | Notes |
|---|---:|---:|---|
| `longmemeval-oracle-temporal-ledger-dated` | **0.7040** | 0.7868 | best result; symbolic temporal ledger on a correctly-dated corpus |
| `longmemeval-oracle-temporal-ledger-control` | 0.6780 | 0.7868 | **paired control** for the row above (`--no-temporal-ledger`) |

The best result is **0.7040**, and it is published with its control arm rather than alone.
The two differ only by `--no-temporal-ledger` — same binary, seed, dataset hash, and corpus
text — so the ledger's effect is measured rather than inferred from a gap between separate
runs. Both artifacts carry `per_query_verdicts`, which is what makes a **paired** comparison
possible:

| Category | n | Control | Ledger | gained / lost | McNemar *p* |
|---|---:|---:|---:|:--|---:|
| **temporal-reasoning** | 133 | 0.4361 | **0.5639** | 22 / 5 | **0.0015** |
| multi-session | 133 | 0.6692 | 0.6541 | 3 / 5 | 0.727 |
| Overall | 500 | 0.6780 | 0.7040 | 26 / 13 | 0.053 |

Read the per-category rows against the *control*, never against another run. `multi-session`
sits below the 0.7143 of the previous best, but the paired arms disagree by two queries at
*p* = 0.73 — that movement is cross-run judge variance, not an effect.

An earlier run shipped this same ledger and measured a **null**. Every excerpt was anchored
to the question's date instead of its own, so relative expressions written weeks apart
collapsed onto one day and the ledger emitted `0 day(s)`. The mechanism was never the
problem; the dates fed to it were. That artifact is gone — the lesson is the durable part.

None of these is a benchmark-leadership claim: the strongest published LongMemEval results
remain higher (Mem0 reports 0.944), and a single run per configuration is not a confidence
interval.
